# 入站报文字段规范（HL7 v2 ER7）

> 本产品从病理相关实验室落盘目录接收加做检查结果（`ORU^R01`）与加做申请（`ORM^O01`），
> 把回报结果按取材部位与蜡块号对回报告，再合成补充报告草稿。
> **本文件是对接任何一家病理 / 检验系统的唯一字段依据**：文档写的，报文就按这个写；
> 解析器读的就是本文列出的字段位。

---

## 1. 适用范围与读者

| 角色 | 关心什么 |
|---|---|
| 免疫组化室 / 分子实验室的接口工程师 | 报文怎么写、哪些字段必填、值取什么 |
| 病理科信息科对接人 | 拒收时看哪一列、为什么这条没进草稿 |
| 本产品的维护者 | 改解析器时哪些字段不能动、改完怎么验证没漂 |

**不在本规范范围内**：出站接口（取基线 / 回写草稿）、基线 JSON 字段、通知通道。
这三块各自另有契约，见 README「命令 / API / 配置说明」。

---

## 2. 报文分流：先看 MSH-9

落盘目录里的每个文件都是一条报文，**按 `MSH-9` 分流**：

| `MSH-9` | 报文流 | 含义 | 处理路径 |
|---|---|---|---|
| `ORU^R01` | 结果侧 | 免疫组化室把加做结果回报回来 | 解析出结果条目 → 去重 → 部位对齐 → 成稿 |
| `ORM^O01` | 申请侧 | 病理科又加做了哪几项，这些检查还要不要做 | 解析出申请条目 → 派生待查项 |

分流依据取 `MSH-9` 的组件 1（消息码）与组件 2/3（触发事件 / 消息结构）。
本产品只认上表两种：其余类型一律拒收并记审计，**不猜**。

**编码**：整份文件先按 UTF-8 读；解不开才**逐行**走「UTF-8 → GBK」回退
（院内报表两种都有，甚至同一个文件里两种都有 —— 不同系统各写各的，导出时被
拼到一起）。逐行回退的好处是：UTF-8 的行不会被整份 GBK 解成乱码，乱码进草稿
就是部位写错。

每份文件的解码方式都留痕：审计流水里 `encoding_detected` 一行记着这份文件是
`utf-8` / `gbk` / `mixed`（混编）读进来的，运行摘要里也有按解码方式的计数。
某一行两种编码都解不开才算坏文件（拒收，code=`bad_encoding`，带行号）。

**行结束符**：`CRLF` 或 `LF` 都认；空行忽略。

## 3. 段结构总览

```
ORU^R01（结果侧）                     ORM^O01（申请侧）
─────────────────────────────         ─────────────────────────────
MSH  报文头（类型/版本/来源）          MSH  报文头
OBR  一次加做申请                     ORC  订单控制动作（新增/取消/…）
  ├─ OBR-2  病理号                    OBR  一次加做申请
  ├─ OBR-3  加做申请号                  ├─ OBR-2  病理号
  ├─ OBR-4  申请项目码                   ├─ OBR-3  加做申请号
  └─ OBR-7  申请时间                    ├─ OBR-4  申请项目码
ZBR  部位信息（蜡块/部位/序号）          └─ OBR-7  申请时间
OBX  一条结果                        ZBR  部位信息（可省）
  ├─ OBX-3  结果项目码
  ├─ OBX-5  结果值
  ├─ OBX-11 结果状态
  └─ OBX-14 结果观察时间
```

**段内顺序**：`ZBR` 段跟在它所属的 `OBR` 段之后，作用于该 `OBR` 组下的所有 `OBX`。
`OBX` 段若出现在任何 `OBR` 之前 → 拒收（code=`orphan_obx`）；
`ZBR` 段若出现在任何 `OBR` 之前 → 拒收（code=`orphan_zbr`）。

**本产品不消费的段**：`PID` / `PV1` / `NTE` 等属于正常报文内容，遇到跳过即可，不算错。

## 4. 字段规范

下表是**本产品真正消费到的字段**。机器校验段落里的每一行都与
`src/patho_supplement/ingest/contract.py` 的字段登记表逐项对账 ——
改了表却没改解析器（或反过来），一致性检查会直接失败。

### 4.1 MSH 段（报文头，两条报文流都适用）

| 段位 | 字段名 | 必填 | 取值域 | 脱敏示例 | 错误处理 |
|---|---|---|---|---|---|
| MSH-1 | 字段分隔符 | 是 | 单字符 | `\|` | 报文首段不足 4 个字符 → 整份拒收（code=missing_field_sep） |
| MSH-2 | 编码字符 | 否 | 组件/重复/转义/子组件分隔符四字符 | `^~\&` | 为空 → 回退默认 ^~\&，不拒收 |
| MSH-3 | 发送方应用（结果来源系统） | 否 | 自由文本 | `IMMUNO-LAB` | 为空 → 来源系统回落 result-inbox（结果侧）/ pathology-system（申请侧） |
| MSH-9 | 报文类型 | 是 | ORU^R01（结果侧）/ ORM^O01（申请侧） | `ORU^R01` | 缺 → 整份拒收（code=missing_message_type）；类型不符 → 整份拒收（code=not_oru / not_orm） |
| MSH-12 | 版本号 | 是 | HL7 版本号（如 2.5.1） | `2.5.1` | 缺 → 整份拒收（code=missing_version） |

> `MSH-1` / `MSH-2` 是**报文自带**的分隔符与编码字符：不同医院的 LIS 可能用别的符号，
> 本产品一律从报文里读，不写死 `|` 与 `^~\&`。

### 4.2 ORC 段（仅 `ORM^O01` 申请侧）

| 段位 | 字段名 | 必填 | 取值域 | 脱敏示例 | 错误处理 |
|---|---|---|---|---|---|
| ORC-1 | 订单控制动作 | 申请侧是 | NW 新增 / CA 取消 / HD 暂停 / DC 终止 / RE 结果随后 | `NW` | 缺 → 拒收该条（reason=missing_control_action）；取值非法 → 拒收该条（reason=illegal_control_action） |

### 4.3 OBR 段（两条报文流都适用）

| 段位 | 字段名 | 必填 | 取值域 | 脱敏示例 | 错误处理 |
|---|---|---|---|---|---|
| OBR-2 | 病理号 | 是 | 自由文本 | `ACC-EXAMPLE-0001` | 空 → 结果侧整份拒收（code=missing_accession）；申请侧拒收该条（reason=missing_accession_no） |
| OBR-3 | 加做申请号 | 申请侧是 / 结果侧否 | 自由文本 | `ORD-EXAMPLE-0001` | 空 → 申请侧拒收该条（reason=missing_order_no）；结果侧留空 |
| OBR-4 | 申请项目码（组件1=码，组件2=名称） | 申请侧是 / 结果侧否 | 组件分隔符 ^ 分隔的码与名称 | `IHC-CD3^CD3^L` | 空 → 申请侧拒收该条（reason=missing_item_code） |
| OBR-7 | 申请时间 | 否 | HL7 时间戳 YYYYMMDDHHMMSS | `20260101101500` | 空 → 结果侧回落为观察时间；仍空则观察时间为空（幂等键该段留空） |

### 4.4 OBX 段（仅 `ORU^R01` 结果侧）

| 段位 | 字段名 | 必填 | 取值域 | 脱敏示例 | 错误处理 |
|---|---|---|---|---|---|
| OBX-3 | 结果项目码（组件1=码，组件2=名称） | 是 | 组件分隔符 ^ 分隔的码与名称 | `IHC-CD3^CD3^L` | 空 → 整份拒收（code=missing_item_code） |
| OBX-5 | 结果值 | 否（空值不进草稿） | 自由文本 | `阴性` | 空 → 不并入草稿，进待人工处理清单 |
| OBX-11 | 结果状态 | 取值受限 | P 初步 / F 终报 / C 更正 / X 无法获得 | `F` | 取值非法 → 整份拒收（code=illegal_result_status）；为空 → 按终报 F 处理 |
| OBX-14 | 结果观察时间 | 否 | HL7 时间戳 YYYYMMDDHHMMSS | `20260101130000` | 空 → 回落 OBR-7；仍空则为空 |

### 4.5 ZBR 段（院内扩展段，两条报文流都适用）

| 段位 | 字段名 | 必填 | 取值域 | 脱敏示例 | 错误处理 |
|---|---|---|---|---|---|
| ZBR-1 | 蜡块号 | 否 | 自由文本 | `B1` | 空 → 不参与一级匹配，进挂起（缺 block_no） |
| ZBR-2 | 取材部位描述 | 否 | 自由文本 | `子宫体` | 空 → 不参与二级匹配 |
| ZBR-3 | 部位序号 | 否（须为整数） | 整数 | `1` | 非整数 → 整份拒收（code=invalid_region_seq） |

## 5. ZBR 段位：院内约定（经验推断）

蜡块号与取材部位描述在 HL7 v2 标准段里**没有对应段位** —— 病理标本的这层信息
各家 LIS 写法不一。本产品用 `Z` 前缀的本地扩展段承载，段位按下表落盘：

| 段位 | 含义 | 院内约定取值 |
|---|---|---|
| `ZBR-1` | 蜡块号 | 制备室给蜡块贴的编号，如 `B1`、`B-3` |
| `ZBR-2` | 取材部位描述 | 登记本上的部位名，如 `子宫体` |
| `ZBR-3` | 部位序号 | 同一份报告内的取材部位顺序，整数 |

**这三行段位是「院内约定（经验推断）」**：本轮没有拿到任何一家医院的真实段位约定，
按病理标本登记的常见写法推定的。正式对接时**以目标医院的实际段位为准**，
差异集中在适配层一处（`src/patho_supplement/ingest/zbr.py`），
不需要改对齐引擎、草稿渲染或回写逻辑。

对接前请确认三件事：

1. 目标医院把蜡块号放在哪个段位（或哪个自定义段的第几个字段）；
2. 部位描述是自由文本还是有标准编码表；
3. 部位序号是整数还是带前缀的串（带前缀则适配层需先剥前缀）。

三个字段**都允许为空**。空就是「不知道」，不是「没有」——
下游据此决定挂起还是降级匹配，绝不拿空值当键去硬对。

## 6. 拒收：两种粒度

| 粒度 | 含义 | 触发场景 | 典型错误码 / 原因 |
|---|---|---|---|
| **整份拒收** | 这份报文整体作废，结果不落库 | 报文头不成型、必填字段缺、关键字段取值非法 | `missing_message_type`、`missing_version`、`missing_accession`、`missing_item_code`、`illegal_result_status`、`invalid_region_seq`、`dirty_extra_separator`、`orphan_obx`、`orphan_zbr`、`not_oru`、`not_orm`、`bad_encoding`、`invalid_segment_name`、`missing_field_sep`、`not_msh`、`empty_message` |
| **条目级拒收** | 只拒这一条，同一份报文里的其余条目照常解析 | 申请侧一条写错（控制动作非法、缺申请号、缺项目码） | `missing_control_action`、`illegal_control_action`、`missing_accession_no`、`missing_order_no`、`missing_item_code`、`missing_obr`、`missing_orc`、`invalid_zbr` |

**为什么分两档**：整份报废会让一批加做全部停摆，那比拒一条糟糕得多；
所以申请侧一条写错只拖这一条，结果侧的关键字段缺失（没有病理号 / 项目码）
则无法归属，才整份拒收。

拒收一律记审计（原因码 + 中文说明 + 段名 + **字段名** + 行号 + 来源文件），
并计入 `malformed` 计数。**绝不静默跳过，也绝不把坏数据塞进草稿。**

### 6.1 脏行：多了一个字段分隔符

有一类行不是「看不懂」，是「看懂了但**错位**」：发送方多写了一个 `|`，
后面的字段整体右移一位 —— 部位序号那一列变成了「子宫体」，蜡块号变成了空。
这种行若静默放过，结果就会绑到错的块上。

判据：**某个字段校验不通过，而把它右移一位就能通过** —— 那就是多了一个分隔符。
命中即单独报 `dirty_extra_separator`，并指明**哪一行、哪个字段**：

| 场景 | 报文里的样子 | 拒收码 | 字段 |
|---|---|---|---|
| `ZBR` 前面多一个分隔符 | `ZBR\|\|B3\|子宫体\|1` | `dirty_extra_separator` | `ZBR-3` |
| `ZBR` 多出第 4 个字段位 | `ZBR\|B3\|子宫体\|1\|2` | `dirty_extra_separator` | `ZBR-4` |
| `OBX` 前面多一个分隔符（结果状态右移） | `OBX\|\|1\|ST\|…` | `dirty_extra_separator` | `OBX-11` |

行尾多一个**空**分隔符（`ZBR\|B3\|子宫体\|1\|`）无害，不拒收。

## 7. 脱敏报文示例

### 7.1 结果侧 `ORU^R01`（正常）

```
MSH|^~\&|IMMUNO-LAB|MICRO-BENCH|RECIPIENT|HOSP-PATH|20260101130500||ORU^R01|MSG-EXAMPLE-0001|P|2.5.1
OBR|1|ACC-EXAMPLE-0001|ORD-EXAMPLE-0001|IHC-CD3^CD3^L|||20260101120000
ZBR|B1|子宫体|1
OBX|1|ST|IHC-CD3^CD3^L||阴性||||||F|||20260101130000
```

解析结果：病理号 `ACC-EXAMPLE-0001`、加做申请号 `ORD-EXAMPLE-0001`、
结果项目码 `IHC-CD3`、结果值 `阴性`、结果状态 `F`（终报）、
蜡块号 `B1`、取材部位描述 `子宫体`、部位序号 `1`、
回报时间 `20260101130000`、来源系统 `IMMUNO-LAB`。

### 7.2 结果侧 `ORU^R01`（更正）

```
MSH|^~\&|IMMUNO-LAB|MICRO-BENCH|RECIPIENT|HOSP-PATH|20260101140000||ORU^R01|MSG-EXAMPLE-0005|P|2.5.1
OBR|1|ACC-EXAMPLE-0001|ORD-EXAMPLE-0001|IHC-CD3^CD3^L|||20260101120000
ZBR|B1|子宫体|1
OBX|1|ST|IHC-CD3^CD3^L|弱阳性||||||C|||20260101140000
```

`OBX-11=C` 是**更正**：取代同（病理号, 蜡块号, 项目码）的旧值，
留一行审计（旧值 → 新值），**不追加成第二条**。
若更正的回报时间比已有结果还早（倒挂），则不取代 —— 较新的原值保留，
更正本身扣下来等人确认。

### 7.3 申请侧 `ORM^O01`

```
MSH|^~\&|PATHOLOGY-REQ|PATHOLOGY-DEPT|IMMUNO-LAB|HOSP-PATH|20260101101500||ORM^O01|ORDMSG-EXAMPLE-0001|P|2.5.1
ORC|NW|ORD-EXAMPLE-0001
OBR|1|ACC-EXAMPLE-0001|ORD-EXAMPLE-0001|IHC-CD3^CD3^L|||20260101101500
```

### 7.4 畸形样例（拒收）

```
MSH|^~\&|IMMUNO-LAB|MICRO-BENCH|RECIPIENT|HOSP-PATH|20260201121500||ORU^R01|EDGE-EXAMPLE-0010|P|2.5.1
OBR|1|ACC-EDGE-0001|ORD-EDGE-0001|IHC-CD3^CD3^L|||20260201120000
ZBR|E1|子宫体|1
OBX|1|ST|IHC-CD3^CD3^L||阴性||||||F|||20260201120000
12|坏行
```

末行段名不合法 → 整份拒收（code=`invalid_segment_name`），并报出第 5 行。

## 8. 字段怎么参与业务规则

| 规则 | 用到哪些字段 |
|---|---|
| **归属三元组**（病理号 + 部位序号 + 蜡块号） | `OBR-2`、`ZBR-1`、`ZBR-3` |
| **幂等键**（病理号 + 蜡块号 + 项目码 + 观察时间 + 结果状态） | `OBR-2`、`ZBR-1`、`OBX-3`、`OBX-14`（缺则回落 `OBR-7`）、`OBX-11` |
| **更正取代** | `OBX-11=C` + 观察时间比较（`OBX-14`） |
| **待查项状态** | `ORC-1`（`NW`/`RE`→待回报；`CA`/`HD`/`DC`→取消/暂停/终止）、`OBR-3`、`OBR-4` |
| **草稿条目来源标注** | `MSH-3`（来源系统）、`OBX-14`（回报时间） |
| **进挂起的字段缺失判定** | `ZBR-1` 缺 → 缺蜡块号；`ZBR-2` 缺 → 缺部位描述 |

---

## 9. 数据边界

- 本产品**只持久化**：病理号、部位序号、蜡块号、项目码、结果值、回报时间。
- **不落**姓名、身份证、联系电话等患者可识别明细；`PID` / `PV1` 段一律跳过。
- 草稿正文只写项目码、项目名、结果值、来源系统与回报时间，
  **不写判读结论**，由病理医师在院内系统签发。

## 11. 规范与实现的一致性校验

规范会漂：改了解析器忘了改文档，或者改了文档忘了改实现。所以有一道机器检查：

```bash
python -m patho_supplement.ingest.contract --check
```

它做三方对账：**规范文档 ↔ 字段登记表 ↔ 解析器源码**。

- 规范里列的字段必须与登记表逐项一致（名称 / 必填性 / 取值域 / 脱敏示例 / 错误处理）；
- 字段一个不多一个不少（登记有规范缺、规范有登记缺都算不一致）；
- 登记的每个字段，取值表达式必须在对应解析模块的源码里真实存在
  —— 规范写了、解析器没读，就是假规范；
- 必填字段的拒收码必须在已知拒收码集合里真实存在。

对账通过退出码 0，不通过退出码 1 并逐条列出不一致之处。
登记表本身在 `src/patho_supplement/ingest/contract.py`，
需要誊写规范表格时用 `python -m patho_supplement.ingest.contract --print-table`
把登记表的当前内容打出来，照抄即可（抄错会被上面这道检查揪出来）。

契约测试在 `tests/test_inbound_contract.py`：逐字段断言「解析值 = 期望值」，
逐字段断言「必填字段缺失时按规范给出的码拒收」。
