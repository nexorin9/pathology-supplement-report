# 规模与性能验收：2000 条 ORU / 300 份报告

> **一句话**：把一天的活量（300 份报告、2000 条加做回报）整个塞进产品真路径，
> 量出**端到端耗时 / 单轮对齐率 / 峰值内存占用 / 状态库体积**四个数，
> 拿阈值卡一道 —— 超阈即不合格。

## 这件事量的是什么

功能测试证明「算得对」，这一轮证明「**扛得住、涨不凶**」。

院内的日常体量是「一天几十到上百份报告、每份 6–10 项加做结果」。守护进程要在
这个量上同时做到三件事，任何一件做不到就不能上院内机：

1. **不慢** —— 一轮跑完不能拖到分钟级，否则回报堆着没人看；
2. **不丢** —— 一条结果只有「进草稿」或「进挂起」两个去向，对齐率不能塌；
3. **不涨** —— 内存不能随运行时长一路涨，状态库不能无界滚大。

跑的是**产品本身**（入站解析 → 幂等去重 → 更正取代 → 待查项派生 → 申请侧闸门
→ 四级对齐 → 成稿 / 挂起），不是另写一套简化判定。基准集那套（见
[对照基准实验](benchmark-comparison.md)）量的是「**对不对**」，这里量的是
「**扛不扛得住**」。

## 规模集从哪来

```bash
python tests/fixtures/generate_samples.py --scale 2000 --flat --out tests/fixtures/scale --seed 42
```

脚本化合成，**固定种子可重跑**（同一种子两次生成逐字节相同）、**断网不失败**
（纯标准库）、**标识一律类目化占位**（不编造住院号、批号、患者化名）。

规模集形态分布（种子 42、2000 条 ORU / 300 份报告）：

| 形态 | 条数 | 为什么要有 |
|------|------|-----------|
| 部位别名 | 300 | 部位描述写法不统一，靠同义词典折算 |
| 蜡块号缺失 | 300 | 回报没带蜡块号 → 挂起等人补 |
| 重复投递 | 300 | 同一结果投两次 → 幂等键只落一条 |
| OBX-11=C 更正 | 300 | 更正取代旧值，不追加成第二条 |
| 回报时间倒挂 | 196 | 更正时间比原值还早 → 不取代，扣下等人 |
| GBK 编码 / 混编 | 2 | 院内报文两种编码混着来 |
| 结果值为空 | 1 | 空值不进草稿 |
| 超长字段 | 1 | 自由文本超长不截断 |

**规模集不入库**（`.gitignore` 已排除 `tests/fixtures/scale/`）：9.5 MB、2202 个文件，
按上面那条命令现场生成即可，指纹固定（`dataset_sha256` 写在报告里）。

## 怎么跑

```bash
# 生成规模集
python tests/fixtures/generate_samples.py --scale 2000 --flat --out tests/fixtures/scale --seed 42

# 跑验收并落报告
python -m patho_supplement.cli benchmark --inbox tests/fixtures/scale/ \
    --scale-report reports/scale.json --scale-work-dir data/scale
```

退出码 `0` = 五项阈值全过；非 `0` = 有超阈项，标准错误里逐条点名是哪一项、
超了多少。报告 `reports/scale.json` 可复核：四项指标、样本量、阈值、逐项判定、
测量环境全在里面。

## 四项指标的口径

| 指标 | 口径 | 为什么不这么算 |
|------|------|--------------|
| **端到端耗时** | 从读第一个文件到跑完落盘的墙钟秒数（`time.perf_counter`） | 只量解析会漏掉对齐与成稿；只量单份报告会说谎 |
| **单轮对齐率** | 并入草稿条目 ÷ 生效结果数 | 分母是「去重与更正取代之后真正要处理的那批」，不是投进来的文件数 |
| **峰值内存占用** | 跑完后的进程峰值 RSS 减去进场时的峰值 RSS | 状态只落 SQLite，中间对象一轮结束就释放 —— 增量涨得多说明有东西被留住了 |
| **状态库体积** | SQLite 主库 + `-wal` + `-shm` 字节数合计 | WAL 模式下刚写的数据可能还在 `-wal` 里，只看主库会低估 |

**对齐率与挂起率互补**：分母同为生效结果数，一条结果要么进草稿、要么进挂起，
没有第三个去向（这条不变量在基准集那轮也单独卡过：错绑定 = 0、无第三去向 = 0）。

## 阈值

| 阈值项 | 环境变量 | 缺省 | 为什么是这个数 |
|--------|----------|------|----------------|
| 端到端耗时上限 | `SCALE_MAX_ELAPSED_SECONDS` | 60 秒 | 实测 1.36 秒；院内机再慢十倍也留得下余量，但慢到分钟级说明某处退化了 |
| 单轮对齐率下限 | `SCALE_MIN_ALIGNMENT_RATE` | 60% | 实测 85.9%；留 25 个点余量，仍高于「大半结果进了挂起清单」的红线 |
| 挂起率上限 | `SCALE_MAX_PENDING_RATE` | 40% | 实测 14.1%；无法获得 / 值为空 / 回报时间倒挂这几类本来就该扣下等人 |
| 峰值内存增量上限 | `SCALE_MAX_PEAK_MEMORY_MB` | 256 MB | 实测 14.6 MB；涨过这个数说明有对象被留住没释放 |
| 状态库体积上限 | `SCALE_MAX_STATE_DB_MB` | 64 MB | 实测 2.80 MB；院内机磁盘不宽裕，别让它无界涨 |

阈值全部可配（环境变量），**配错直接拒绝启动并点名是哪一项** —— 不静默改用缺省值。
`doctor` 子命令的「生效阈值与运行参数」表里能查到这五项的当前值。

## 本机实测结果

测量环境：Python 3.10.20 / CPython｜macOS-26.5.1-arm64｜10 核｜2026-10-28

样本量：**2200 个报文文件**（2000 条 ORU^R01 + 200 条 ORM^O01）→ **300 份报告** →
去重与更正取代后 **1400 条生效结果**（重复投递 300 条、更正取代 300 条）→
草稿 **300 份 / 1203 条**、挂起 **197 条**。

| 指标 | 实测 | 阈值 | 判定 |
|------|------|------|------|
| 端到端耗时 | 1.36 秒 | ≤ 60 秒 | 过 |
| 单轮对齐率 | 85.9%（1203/1400） | ≥ 60% | 过 |
| 挂起率 | 14.1%（197/1400） | ≤ 40% | 过 |
| 峰值内存增量 | 14.6 MB（进程峰值 RSS 43.6 MB） | ≤ 256 MB | 过 |
| 状态库体积 | 2.80 MB（2 940 928 字节） | ≤ 64 MB | 过 |

对齐判定分布：L1 蜡块号精确 603 条、L2 部位描述精确 600 条、L3 词法模糊 0 条、
L4 挂起 0 条 —— 规模集里没有一条是靠「猜」并进草稿的，也没有一条正常回报落到 L4。

多路召回路况：14097 把检索键全部成功（失败 0、超时 0），合并 7661 条去重后留
1203 条（去掉重复 6458 条）。

## 换个机器复现

```bash
python -m patho_supplement.cli benchmark --inbox tests/fixtures/scale/ \
    --scale-report reports/scale.json
```

报告里的 `environment` 段记着本次的 Python 版本、平台、CPU 核数与测量时刻，
`sample.dataset_sha256` 记着规模集指纹 —— 换了机器、换了种子，数字对不对得上
一眼就能看出来。耗时与内存会随机器变，**对齐率与挂起率不会**（同一批数据、
同一段代码，结果是确定的）。

## 这轮没量的东西（说清楚边界）

- **真实院内数据**：本轮不可得。经核验，没有公开数据集携带「病理号 + 取材部位 +
  蜡块号 + 免疫组化加做回报」这层结构，所以规模集是脚本化合成的**脱敏样例**。
  它不是院内真实数据，只是体量与形态分布与真实批次一致。
- **出站回写耗时**：规模集只跑批处理重放（不真正回写病理系统）。出站耗时取决于
  院内网络与病理系统响应，不适合在本机量 —— 那一段由出站契约测试与超时/重试
  机制兜底。
- **并发**：本轮是单进程单轮。守护进程常驻时的内存稳定性由「一轮结束释放中间
  对象」那条不变量与 `test_daemon.py` 的相关用例守住。
